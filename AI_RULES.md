# AI RULES

## 1. Purpose

These rules govern every AI agent, automated tool and contributor working on the Sing The Easy Way website repository.

Sing The Easy Way is an elite, diagnosis-led, owner-delivered, high-trust vocal-coaching practice.

The governing commercial standard is elite. The business, website, coaching, brand, commercial position and intended client experience must not be described as merely premium.

Elite positioning must be demonstrated through specialist judgement, selective service architecture, disciplined evidence, direct owner delivery, discretion, restraint and clear commercial boundaries. It must not be simulated through empty luxury language, artificial exclusivity, invented prestige, unsupported credentials, fabricated scarcity or guaranteed outcomes.

## 2. Authority order

Resolve conflicts in this order:

1. Matt Thompson's newest explicit instruction.
2. `Project_Master_Context_v1.md`.

## 5. Elite positioning standard

Every material website decision must strengthen this position:

> Sing The Easy Way provides elite, diagnosis-led, owner-delivered vocal coaching through private, live, one-to-one online work for contemporary and popular singers.

The website must prioritise:

- diagnosis before exercises;
- root-cause analysis;
- Matt's individual judgement;
- direct owner delivery;
- work applied inside real music;
- protection of the singer's recognisable identity;
- disciplined and verifiable proof;
- confidential handling of professional work;
- deliberate hierarchy;
- restrained design;
- selective, high-trust conversion routes.

The website must avoid:

- low-ticket framing;
- repeated price-first selling;
- crowded retail cards;
- casual lesson-shopping language;
- generic exercise-led claims;
- equal-weight service menus that encourage buyers to choose primarily by price;
- empty luxury wording;
- invented exclusivity;

- exaggerated transformations;
- artificial urgency or scarcity;
- repeated calls to action that make the practice feel transactional.

The word `elite` may describe the intended position and standard. It must not be used as a formal product name, repeated as unsupported self-praise or substituted for evidence.

## 18. Bounded autonomous execution

When Matt gives one explicit, bounded repository instruction, it authorises the complete stated sequence within its declared scope:

- checking the active branch and repository state;
- reading required files;
- inspecting dependencies;
- editing authorised files;
- local validation;
- complete diff review;
- staging authorised files;
- creating the specified commit;
- pushing to the specified branch;
- opening or updating exactly one authorised pull request.

Do not request conversational approval between authorised stages.

Do not stop after inspection, editing, validation, commit or push when the full sequence has already been authorised.

Combine independent read-only checks.

Combine staging, commit and push where technically practical.

Do not request approval for temporary-file cleanup.

Do not repeat successful commands.

Do not repeat denied commands.

Do not restart completed discovery or blocked browser testing.

Platform security prompts are controlled by Copilot Tool permissions, not repository documentation.

Matt may select:

`Tool permissions: Unconditional approval / Allow All`

Allow All does not extend the authorised scope and does not independently authorise merge, deployment, publication, branch deletion, force-push, destructive reset, rebase, settings changes or protected-system changes.

## 19. Branch and release control

Before editing, confirm:

- current branch;
- working-tree state;
- declared scope;
- pull-request state when relevant;
- whether the working branch is based on current `origin/main`.

Use the working branch authorised in Matt's current instruction.

Do not assume a historical branch remains authorised.

Keep a recoverable Git history.

Do not use force-push, destructive reset, destructive checkout, rebase of shared work, branch deletion, git stash or worktrees unless Matt explicitly authorises the exact action.

A commit, push or pull request is not publication.

Distinguish accurately between:

1. edited locally;
2. saved in the working tree;
3. committed;
4. pushed;
5. included in a pull request;
6. merged into `main`;
7. deployed;
8. verified on the live domain.

Before committing an implementation, run:

```bash

python3 assets/scripts/check-site.py
git status --short -- app/ worker/
git status --short
git diff --stat
git diff --name-only
```

Review the complete diff.

Validate:

- elite positioning is preserved or strengthened;
- merely premium framing is absent;
- approved prices and routes remain exact;
- General Enquiry is not presented as free coaching;
- professional enquiries remain separate;
- `bookingOptions` remains unchanged;
- analytics and consent remain unchanged unless explicitly authorised;
- no former review-platform reference returns;
- one H1 remains on each changed public page;
- links and asset paths resolve;
- no placeholders remain;
- keyboard focus and contrast remain accessible;
- no horizontal overflow is introduced;
- approved binaries remain unchanged unless explicitly authorised;
- protected areas remain untouched;
- only authorised files changed.

## 21. Stop conditions

Stop before commit, push, merge or deployment if:

- the active branch is uncertain;
- current `main` cannot be established when required;
- a required source file is missing;
- a protected area would change without authority;
- a Jotform route differs from the approved register;
- General Enquiry would be presented as free coaching;
- professional enquiries would be routed through the consumer payment form;
- an unverified analytics identifier or secret is required;
- the checker reports an unapproved failure;
- the work requires invented evidence, pricing, claims or destinations;
- a genuine merge conflict occurs;
- a secret or personal data would be exposed.

Report the blocker, last known safe commit, affected files, smallest safe next action and rollback point.

Do not describe partial work as complete.

## 22. Definition of done

A bounded website task is complete only when:

- the declared scope is complete;
- elite positioning has been preserved or strengthened;
- no merely premium, generic or retail framing has been introduced;
- approved prices and destinations remain correct;
- only authorised files changed;
- protected areas remained untouched;
- the complete diff was reviewed;
- required validation passed;
- the specified commit was created;
- the authorised branch was pushed;
- exactly one authorised pull request was opened or updated;
- the final repository and publication state was reported accurately.

Merge, deployment and publication remain separate stages requiring Matt's explicit authority.
